## 1. Delivery Agent (`apps/agent-runtime/src/agents/delivery/agent.py`)

### Responsabilidade

Orquestrar a entrega final ao cliente após QA aprovado: gerar PDF de entrega e tutorial em vídeo em paralelo, depois notificar o cliente.

### Sub-agentes / Tasks

```
DeliveryAgent (claude-sonnet-4-6)
  parallel_group=1 (executam simultaneamente):
    GeneratePDFTask    → tasks.py:generate_delivery_pdf()  [já implementado]
    GenerateTutorialTask → POST /api/v1/internal/heygen/generate
  NotifyClientTask (após ambos completarem):
    → POST /tasks { task_type: "messaging.send", channel: whatsapp/telegram }
    → envia PDF + link do vídeo ao cliente
```

### Endpoint interno Node.js (novo)

```
POST /api/v1/internal/heygen/generate
Body: { projectId: string, siteUrl: string, businessName: string }
Response: { videoUrl: string, thumbnailUrl: string }
Auth: header interno X-Internal-Token (secret compartilhado via SecretsProvider)
```

- Chama `HeyGenAdapter` (já existe em `apps/api/src/infrastructure/integrations/`)
- Cria HITL `APPROVE_STAGING` com preview da URL do vídeo antes de enviar ao cliente
- Retorna URL do vídeo gerado

### Payload de entrada (`task_type: "delivery.generate"`)

```python
class DeliveryInput(BaseModel):
    project_id: str
    site_url: str
    admin_url: str
    business_name: str
    lighthouse_scores: dict  # {performance, a11y, seo, best_practices}
    owasp_status: str        # "passed" | "failed"
    correlation_id: str
```

### Fluxo de erro

- PDF falha → task retorna `failed`, não envia nada ao cliente
- HeyGen falha → entrega somente PDF (degradação graceful, sem falhar o delivery todo)
- Notify falha → task retorna `failed`, operador notificado via HITL

## 2. Deploy Trigger pós-builder

### Onde vive

`apps/api/src/application/agent/AgentExecutionService.ts` — método que processa resultados de tasks retornadas pelo Python runtime.

### Lógica

```typescript
// Quando task_type === "builder.generate" && status === "completed"
await createHITLApprovalUseCase.execute({
  actionType: HITLActionType.APPROVE_STAGING,
  projectId: result.payload.projectId,
  operatorId: project.operatorId,
  payload: {
    sitePreviewUrl: result.payload.previewUrl,
    buildLog: result.payload.buildLog,
    builderModel: result.payload.model,
  },
  expiresInMinutes: HITLTimeouts[HITLActionType.APPROVE_STAGING],
  correlationId: result.correlationId,
});
```

### Ao aprovar HITL `APPROVE_STAGING`

`ApproveHITLUseCase` detecta `actionType === APPROVE_STAGING` e chama:

```typescript
await deploymentRouter.deploy({
  projectId: hitl.projectId,
  platform: project.deployPlatform, // Vercel | Netlify | CloudflarePages | Render
  siteFiles: await storage.getSiteFiles(project.buildArtifactPath),
});
```

Emite `ProjectDeployed` domain event com a URL final.

### Segurança

- Deploy de produção NUNCA acontece sem HITL aprovado (invariante verificado em `ApproveHITLUseCase`)
- `APPROVE_STAGING` timeout: 120 minutos / 2h (conforme `HITLTimeouts`)

## 3. WhatsApp webhook → Briefing Extraction Automática

### Session key no Redis

```
Chave:  whatsapp:{E164phone}
Valor:  briefingId (UUID)
TTL:    86400s (24h)
```

`StartBriefingUseCase` (existente) recebe `contactPhone` do lead e grava a chave após criar o briefing.

### Acumulação de mensagens

```
Chave:  whatsapp:transcript:{briefingId}
Valor:  JSON array de { from, body, timestamp }
TTL:    86400s
```

Cada mensagem recebida via webhook é appended (Redis `RPUSH`).

### Trigger de extração

Extração automática dispara quando **qualquer** das condições:

1. Mensagem contém palavra-chave de finalização: `"ok"`, `"pronto"`, `"pode"`, `"isso"`, `"sim"` (case-insensitive, início de mensagem curta ≤ 10 chars)
2. Operador chama `POST /api/v1/briefings/:id/extract` manualmente (fallback sempre disponível)

Ao disparar:

```typescript
// whatsapp.webhook.routes.ts
const briefingId = await redis.get(`whatsapp:${from}`);
if (briefingId) {
  const transcript = await redis.lrange(
    `whatsapp:transcript:${briefingId}`,
    0,
    -1,
  );
  await agentRuntimeClient.post("/tasks", {
    task_type: "briefing.extract",
    payload: { briefingId, transcript: transcript.join("\n") },
  });
  await redis.del(`whatsapp:${from}`); // limpa sessão
}
```

### Escopo limitado

- Só ativa se `redis.get(whatsapp:{phone})` retorna valor (briefing em andamento)
- Mensagens normais (sem sessão ativa) não são afetadas

## 4. E2E CI Fix

### Problema

Job `e2e` no CI falha porque `.next/standalone/` não é copiado antes de `next start` no modo standalone.

### Fix

```yaml
# .github/workflows/ci.yml — job e2e, após o build step
- name: Prepare Next.js standalone
  run: |
    cp -r apps/web/.next/static apps/web/.next/standalone/.next/static
    cp -r apps/web/public apps/web/.next/standalone/public
  working-directory: ${{ github.workspace }}
```

`output: "standalone"` já está em `next.config.ts`. O fix é apenas copiar os assets estáticos que o Next.js não copia automaticamente.
